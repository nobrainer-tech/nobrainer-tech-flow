# nobrainer-tech-flow 2.3.2: install, update and undo without false alarms or leftovers

Release date: 2026-10-14.

Run undo twice and the second run no longer fails. Undo leaves your profile as it was
before the setup, including the empty folders the installer had to create. An update
through `install.sh` delivers the new instruction block. A repeat apply says that
nothing changed instead of asking you to restart your client. These six fixes came
from a test of a fresh install that followed the README commands on 2.3.1.

## What changes

- **A second undo is a clear no-op.** `--undo` and `--undo --apply` with no setup
  record print `NOTHING TO UNDO`, name the client and the record they looked for,
  write nothing and exit 0, in `install.sh`, `install.py` and the npm command. In
  2.3.1 they exited 3 with `rollback state not found`. A damaged or unreadable
  record, a folder or link where the record should be, and a record that only the
  Python undo can read still stop with an error.
- **Undo removes the folders the setup created.** The setup record gains
  `created_dirs`, the folders the setup had to create (links resolved, an empty list
  included). Undo removes each one that is still empty, deepest first. A folder that
  existed before the setup, or holds anything else, stays. A record from 2.3.1 or
  earlier has no list and keeps the earlier rule, so its undo removes only an empty
  skills folder. A list that names a folder the setup cannot have made (a relative
  path, `..`, the root, a folder beside the setup's own, a duplicate, an entry that
  is not text) is refused with exit 3 and nothing is changed. The `.bak` copy the
  setup made of an instruction file you already had is kept, as before.
- **`install.sh` replaces a block of an earlier version.** When the managed block
  differs from this version's text, `install.sh` replaces it from the start marker to
  the end marker and keeps every byte outside them (line endings, a byte order mark,
  a missing final line break). The file as it was is saved as a `.bak` copy first,
  the preview shows the lines that change, and undo still removes the block or puts
  back the file from before the setup. A block that carries an option (a standing
  authorization, a saved wiki root or a preference), or whose markers do not stand on
  lines of their own, is still left as it is with a note that points to
  `install_personalization.py --keep-options`; `install.py` keeps rewriting such
  blocks and keeping their options.
- **The block names the module the way the client lists it.** Codex 0.157.1 lists the
  module as `nobrainer-tech-flow:nobrainer-tech-flow` when a plugin manifest sits
  above the folder a link resolves to, which is the case for a git checkout and for the
  npm package, and as `nobrainer-tech-flow` for a copy. It adds the module text to the
  request only for the name it lists. The entrypoint line of the block and the install,
  naming, testing and compatibility docs now say to use the listed name and give both
  Codex forms. The README and the repository instruction files (`AGENTS.md` and
  `CLAUDE.md`) give the same rule. Existing blocks differ from the new text, so the
  next apply updates them (`install.sh` through the replacement above, `install.py`
  as before).
- **A repeat apply says nothing changed.** When no link and no instruction file was
  written, apply prints `UP TO DATE` and no restart hint. `INSTALLED` and the restart
  hint stay for a run that changed something.
- **The setup record and file modes are documented.** The installer writes
  `.nobrainer-flow-onboarding-<client>.json` in the chosen home with mode 0600. A new
  instruction file is created with mode 0600 as well; an existing file keeps its mode
  and so does its `.bak` copy. Undo deletes the record. [Installation](../INSTALL.md)
  describes the file and its fields.

Both installers behave the same. The scripts, the npm command that calls
`install.py` and the guided `--rollback` read and write one record.

## Scope and distribution

This is an installer and documentation fix. The eighteen module contents are unchanged
from v2.3.1 except for the entry module's `VERSION` file. No workflow, model-routing
or performance change is claimed.

Two limits remain. The guided `recommend_flow_setup.py --rollback` with no record
still exits 3 with `rollback state not found`, and an npm undo that finds a record but
no retained release files still exits 3. Neither is part of the second-undo case.

The Codex naming check covers Codex 0.157.1 on macOS, with a typed name and a linked
mention sent through `codex exec` to a local stand-in server. It does not show what a
model does when it sees the plain form in a listing that names the module under the
plugin, and it did not drive the terminal or desktop mention pickers, other Codex
versions or operating systems, or a plugin-channel install. The
[compatibility record](../COMPATIBILITY.md) has the readback.

The native plugin 2.3.2 will carry the same installer. Plugin export, publication and
target-client import each require their own readback. npm registry publication is
still pending; source release files and a locally packed tarball do not establish
registry availability.

## Rollback

Return to the reviewed v2.3.1 source through the documented preview and undo flow.
Undo a 2.3.2 setup with 2.3.2 scripts when you can. The 2.3.1 `install.sh` cannot read
a 2.3.2 record and points you to the Python undo. That undo reads the record and
removes the links, the block and the record, but it does not know the folder list, so
the empty folders the setup created stay. A setup recorded by 2.3.1 and undone by
2.3.2 leaves them too, because its record has no folder list. Keep retained source
files while any client links refer to them.
