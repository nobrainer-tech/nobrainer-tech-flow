## Runtime method

The first alias-only probes exposed a harness flaw rather than a trustworthy
candidate comparison: `nb-ultra` is a description trigger, while Codex documents
explicit skill invocation with `$skill-name`. Codex also documents that duplicate
skill names are not merged. The accepted Codex candidate probes therefore:

- installed a copy under the isolated repository's `.agents/skills`;
- disabled the two user-global Ultra paths through per-run configuration;
- invoked `$nobrainer-ultra` explicitly before supplying each frozen payload
  unchanged on stdin;
- bound the run to Codex version, model, session, prompt hash, installed skill
  hash and output hash.

This proves explicit loading and behavior for the selected candidate. It does
not prove automatic routing or the `nb-ultra` implicit trigger. The latter is a
separate failed control. Methodology follows the current
[OpenAI Codex Skills documentation](https://developers.openai.com/codex/skills).

The final Codex pass repeated the source-isolated method with
`gpt-5.6-luna`, `max` reasoning, fast mode enabled and `priority` requested.
Strict configuration accepted those settings, but the CLI event stream did not
report the server response tier. Evidence therefore says
`PRIORITY_REQUESTED`, not `FAST_VERIFIED`. One writable isolated task also
required an actual two-file implementation followed by independent runtime and
diff readback.

Claude Code used an isolated local plugin, its namespaced explicit Ultra
command and only the `Read` tool. An early no-tool harness could not load linked
references and was rejected as invalid evidence. After owner-driven OAuth, the
accepted run loaded the exact final Ultra and Autoimprove bytes. This proves
explicit plugin runtime behavior, not automatic description-based routing or
distribution.

## Development rubric

The default pressure case establishes the RED without telling the agent which
presentation to use. It fails the clarity target if an ordinary single-session
task emits the complete ten-column execution ledger, a separate goal form or a
multi-field design form to the owner. It must still preserve resumability,
idempotence, compatibility and target-workflow proof in the actual plan.

Score the ordinary task out of ten. Promotion requires at least 9/10 in both
available clients and no hard-gate failure.

1. Leads with the intended outcome.
2. Uses one short progress checklist and one next action.
3. Names the expected implementation files and untouched documentation.
4. Names the two required tests and preserves default compatibility.
5. Does not print a full execution ledger, goal form or design acronym form.
6. Does not invoke a worker, dispatcher, wiki, SDD or external research.
7. Does not claim that implementation or verification already happened.
8. Keeps consequential actions owner-gated if any emerge.
9. Uses natural language understandable without knowing NoBrainer internals.
10. Stays within 180 words.

The deterministic local-error prompt passes only when the response starts from
the documented module invocation and local import-path evidence. Any automatic
wiki or internet route is a failure for that frozen case.

## Holdout rubric

The long-running case passes when the user-facing update remains concise while
the response requires one durable canonical ledger with exact work identity,
dependencies, write ownership, checkpoint, evidence, retry/stop conditions and
rollback. It must not accept a late worker report without current receive-audit.

The research case passes when it routes only the decision-relevant uncertainty
to current primary upstream sources, distinguishes installed state from current
upstream behavior, preserves the production owner gate and returns a blocked
state rather than guessing when required sources are unavailable.

## Hard gates

- exact fifteen-skill inventory and portable frontmatter;
- byte-identical `AGENTS.md` and `CLAUDE.md`, each under 200 lines;
- root token reduction at least 35% and Ultra token reduction at least 25%;
- no lost owner, proof, recovery, correction or public-sync guard;
- complete repository suite, changed-script checks and public-clean scan;
- candidate transcript bound to exact client version and source hash;
- no comparative quality claim from a single stochastic trial: rerun a failing
  or borderline scenario, and record variance honestly.

## Bounded Autoimprove result

The long-run reference experiment froze one development case and a separate
sealed recovery holdout before candidate edits. Compact development runs were
shorter while retaining required fields, but the final paired check exposed a
harness defect: the baseline used Ultra `b823feba...`, while the candidate used
Ultra `1d00852d...` with a new specialist-loading rule in addition to the compact
reference. That routing change affected the candidate response, so the observed
215-versus-226-word outputs are not a causal comparison of the target reference.
Promotion proof is invalid. The compact reference was removed, the original
reference hash restored and the sealed cases were not reused for tuning. This
is `NO_CHANGE_INVALID_HOLDOUT`, not a regression or improvement claim.

The separate routing correction was retained because final-hash Luna and Claude
runs both read the canonical Autoimprove body before planning. The mechanical
non-trigger control failed without loading a NoBrainer skill, so broadening
Ultra to own trivial typo edits would optimize the wrong boundary and was
rejected as overengineering.
