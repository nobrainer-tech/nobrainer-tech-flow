# Done gap: Flow against plain Claude Code on early "done" — 2026-11-21

The question: on tasks where an agent can easily say "done" too early, does Flow raise the
share of tasks that are really done, or cut false "done" claims? It follows the token-cost
eval ([2026-11-14](token-cost-2026-11-14.md)), where plain Claude Code passed all eleven
tasks and Flow could show no benefit.

## Method

Tasks, hidden checks, reference solutions and the decision rule were committed before any
agent run, in `d29f3cb`: [tasks](artifacts/done-gap/tasks.md),
[scoring](artifacts/done-gap/scoring.md), [base](artifacts/done-gap/make_base.py),
[task folders](artifacts/done-gap/tasks/), [runner](artifacts/done-gap/run.py),
[grader](artifacts/done-gap/grade.py), [counter](artifacts/done-gap/score.py).

- Ten tasks on the `shop` fixture, one per way an agent says "done" too early: a second copy
  of a business rule (D1), rules in `CONTRIBUTING.md` (D2), data variety in archived files
  (D3), an eight-criterion spec (D4), HTML with untrusted names (D5), an idempotent migration
  with a broken file (D6), a CLI that goes through another module (D7), a test that fails
  under 9 of 50 hash seeds (D8), Decimal everywhere (D9), a rename with a deprecated alias
  (D10).
- Calibration before the runs: each hidden check failed on the task's starting repo, passed
  three times on the reference solution, and failed on the obvious incomplete fix. Three
  hidden checks were loosened before freezing because they asked for more than the prompt
  said (tie order in D2, progress lines on stderr in D6, the name `float` in D9).
- Arms: **PLAIN**; **FLOW**, the 18 skills of `2fe1c41` installed in the project with
  `adapters/bootstrap.md` as `CLAUDE.md`; **FLOW_ASK**, FLOW with `Use NBFlow. ` before the
  prompt.
- Claude Code CLI 2.1.329 in print mode, `claude-opus-5-5` at `medium`, project settings
  only, web tools off, a fresh copy per run, two runs per task and arm (60 runs), at most one
  retry turn. Cost is the client's `total_cost_usd`, a list-price estimate.
- Manipulation check passed: every FLOW and FLOW_ASK run listed `nobrainer-tech-flow`, no
  PLAIN run did.

What the numbers say:

- **Plain Claude Code did not fall into any trap.** It found the second copy of the rule,
  read `CONTRIBUTING.md`, ran the CLI on every archive file, reproduced the flaky test under
  many seeds and kept the test file unchanged. On Opus 5.5 at medium the early "done" these
  tasks were built around did not happen, so Flow had nothing to catch.
- **An installed Flow does not run unless asked.** Its entry skill ran in 0 of 20 FLOW runs
  (1 of 12 on 2026-11-14). FLOW therefore measures the cost of the loaded text: 1.11 times,
  the same fixed amount per session seen before.
- **When asked, Flow costs about half as much again** and takes more turns (median 12.5
  against 9), with no gain in completion on this set.
- **The one failure is Flow's own.** In D4 (FLOW_ASK, second run) Flow followed its worktree
  rule and wrote the change into a new worktree on branch `feat/returns`, leaving the
  user's checkout unchanged; the hidden check ran there and failed. The code itself was
  right: the retry turn moved it into the checkout and passed (cost 0.456 plus 0.538). The
  final message named the branch but said "Not checked: None" and did not say the checkout
  was unchanged. The grader counts it as a false "done"; MAIN's hand label does not. Either
  way the verdict is `EVEN`.

## Limits

- Ten tasks, two runs per arm, one model and effort, print mode only. With every PLAIN run
  passing, the set cannot show a benefit; it can only show that none appeared.
- Hand labels: scoring asked for ten; only one run failed turn 1, so one was labelled, and
  the grader disagreed with it (reported above, both readings).
- Changed after review, after the runs: the D2 hidden check now accepts any of the tied
  orders at the `--top` cutoff (it had required two specific ones), and `score.py` refuses a
  verdict when a client turn ended with a non-zero exit or `is_error`. Neither changes a
  reported number: all six D2 runs passed the stricter check, and the counter's
  verdict came from runs that all produced a final result and passed their check. The raw
  run directories were not kept, so client exit codes cannot be rechecked now.
- The tasks are single-session and the prompt is the whole brief. Not covered: long
  multi-session work, resumption after a crash, and weaker models or lower effort, where an
  early "done" is more likely.

## Consequence

- No public sentence may say that Flow catches false "done" or raises completion. On 21
  tasks across two evals, plain Claude Code on Opus 5.5 completed every task on the first
  turn, and an installed Flow did not run on its own.
- Flow's worktree rule is a defect for a user working in one checkout: the work lands where
  the user does not look. Fix: create a worktree only when the user or the project asks for
  one, otherwise work in the current checkout on a branch.
- Next measurement that could show Flow's value, if it exists: the same tasks on a weaker
  setting (Sonnet 5.5 or Opus 5.5 at low effort) and multi-session tasks with a handoff.
  Until then the case for Flow rests on its owner gates and handoff, not on completion.
